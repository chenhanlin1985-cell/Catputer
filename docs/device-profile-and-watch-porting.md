# 多端 Profile 与手表适配准备

本文用于把 Catputer 的端侧适配方式收拢成一个可继续扩展的约定。目标不是马上把项目完整移植到手表，而是先让 Cardputer、Waveshare 触屏端、未来手表端都能按同一套边界开发，避免后续越改越乱。

## 当前端侧

| Profile | PlatformIO 环境 | 入口文件 | 主要交互 | 适合定位 |
| --- | --- | --- | --- | --- |
| `cardputer` | `m5stack-cardputer` | `src/main.cpp` | 键盘、Fn 组合键、SD 卡、扬声器、本地 TTS、BLE 键盘 | 随身文字输入、提醒、轻量聊天 |
| `waveshare_amoled_18` | `waveshare-amoled-18` | `src/main_waveshare_lvgl.cpp` | 触摸、两颗实体键、AMOLED、SD_MMC、ES8311、本地 TTS、PC 同步 | 展示陪伴、触屏互动、桌面/移动端侧 |
| `watch_touch` | 待新增 | 待新增 | 小屏触摸、震动、抬腕/唤醒、电池/休眠 | 手表化陪伴、提醒、快捷回应 |

后续新增设备时，优先新增 profile，不要直接把条件判断塞进现有入口文件。

## 分层边界

### 宠物核心层

这部分应该尽量和设备无关，可以被所有端侧和桌面端复用。

- 宠物状态：饱腹、心情、体力、清洁、亲密度。
- 宠物身份：`id`、`name`、`kind`、`personality`。
- 记忆与事件：最近记忆、轻提醒、时间场景、天气场景、重逢场景。
- 同步快照：`sync_enter`、`sync_ping`、`sync_leave` 以及 `snapshot.pet`。
- 资源标识：只传 `kind` 等形象标记，不在同步协议里传大图。

### 设备适配层

这部分每个 profile 可以不同，不要强求统一。

- 屏幕尺寸、色彩、刷新方式。
- 输入方式：键盘、触摸、实体键、旋钮、手势、抬腕。
- 存储后端：Cardputer 使用 `SD`，Waveshare 使用 `SD_MMC`，手表可能没有 SD。
- 音频后端：Cardputer 和 Waveshare 的扬声器链路不同，手表还要重新验证。
- 电源管理：电量、休眠、唤醒、低功耗刷新。
- 网络策略：按需联网，不把开机联网作为所有设备的硬依赖。

### 表现层

表现层允许完全不同，但要表达同一套宠物状态。

- Cardputer：键盘优先，小屏信息密度要低。
- Waveshare：触摸优先，适合卡片、滑动和更大的宠物展示。
- 手表：只保留最关键的信息，强调“抬手看一眼”和“点一下回应”。

## Device Profile 建议字段

端侧广播、PC 设备注册表、同步快照里建议保持这些字段稳定：

```json
{
  "device": {
    "id": "waveshare-touch-d4db1c",
    "type": "waveshare_amoled_18",
    "name": "Catputer Touch",
    "caps": {
      "touch": 1,
      "keyboard": 0,
      "mic": 1,
      "speaker": 1,
      "vibration": 0,
      "battery": 1,
      "sleep": 0
    }
  }
}
```

新增能力位时遵循两个原则：

- 能力位表达“硬件或固件当前是否可用”，不要表达 UI 按钮是否显示。
- 旧端侧看不懂的新字段必须可以忽略，不能导致同步失败。

## 手表端最小 MVP

手表端不要一开始追求完整聊天，它更适合先做一个很稳的小陪伴端。

1. 启动后显示宠物、名字、心情/亲密度、电量。
2. 点击宠物触发一句短反馈和轻微动画。
3. 左右滑切换：主页、提醒、天气、同步。
4. 支持 PC 端“进城/出城”同步，能接收指定宠物。
5. 支持断线保护：同步中断时端侧能回到安全状态，PC 不产生重复宠物。
6. 支持低功耗：无操作一段时间后降低刷新或熄屏，触摸/按键/抬腕唤醒。

暂时不建议在手表 MVP 里做：

- 全量中文输入法。
- 自由语音转文字。
- 长篇 AI 聊天。
- 大量图片纪念卡。
- 复杂猫仓管理。

这些能力更适合放在 PC 端或手机端，手表端只负责呈现、提醒和快捷回应。

## 手表 UI 规格建议

手表屏幕可能是 240x240、360x360、390x390、466x466 等尺寸。后续 UI 不应依赖固定坐标，而应从 profile 读取屏幕尺寸。

建议布局：

- 顶部：电量、联网状态、同步状态。
- 中央：宠物大图，默认占屏幕宽度的 35% 到 55%。
- 宠物下方：名字和一句短状态。
- 底部：最多 2 到 3 个快捷入口，例如“摸摸”“提醒”“回家”。

资源建议：

- 保留像素原图作为主资源，例如 16x16、32x32。
- 由渲染层按设备倍率放大，不要为每个屏幕手工画一套。
- 手表端建议至少支持 2x、3x、4x 放大。
- 大背景图不要作为核心依赖，优先用程序绘制的简单场景，降低内存压力。

## 网络与语音策略

手表端应该默认离线可用，联网只作为增强。

- 离线可用：宠物显示、状态衰减、短句反馈、提醒、本地事件。
- 需要联网：天气刷新、AI 聊天、新闻/新鲜事、PC 同步。
- 本地可尝试：TTS 播报、固定命令识别。
- 不建议放在 ESP32-S3 手表本地：自由语音转文字、长文本 LLM 推理。

如果手表是 Android 类设备，可以重新评估语音和联网，因为它的系统能力会比 ESP32-S3 设备强很多。

## 后续实施顺序

1. 先把新增端侧都登记成 profile：`type`、屏幕尺寸、输入能力、音频能力、电源能力。
2. 把同步协议里和设备相关的字段稳定下来，PC 猫仓只看 profile，不写死 Waveshare 或 Cardputer。
3. 把 UI 坐标逐步改成根据屏幕尺寸计算，先从新端侧做，不强行重构已经稳定的 Cardputer。
4. 做一个 `watch_touch` 空 profile 文档和最小入口，等具体手表型号确定后再补驱动。
5. 最后再考虑低功耗、震动、抬腕、传感器等手表特性。

## 开发约束

- 不要为了适配手表改坏 Cardputer 和 Waveshare 已经收住的核心路径。
- 不要把 PC 猫仓功能搬到端侧，端侧只做驻留、陪伴和轻交互。
- 不要把聊天作为手表端的第一目标，提醒和陪伴反馈更重要。
- 不要在同步协议里塞大资源，资源仍由各端侧根据 `kind` 自己渲染。
- 每次新增 profile 后，都要补充构建、烧录、串口、资源规格和已验证能力。
