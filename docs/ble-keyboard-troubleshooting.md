# BLE 键盘输入卡顿排障记录（Cardputer / Catputer）

本文记录一次已复现并修复的 BLE 键盘模式问题，便于后续快速定位同类故障。

## 问题现象

- 蓝牙已连接，但输入几个字符后明显延迟。
- 继续输入会卡住，偶发连续重复字符（例如一串 `aaaa...`）。
- 部分场景下看起来像“无响应”，但设备并未重启。

## 根因结论

问题是多因素叠加，不是单点故障：

1. BLE 模式切入后，主循环仍运行部分网络/同步逻辑，造成时序干扰。
2. 早期按键发送策略在高频输入下容易形成发送拥塞。
3. 队列满时若处理不当，会放大“按下/抬起”不对称风险，表现为重复输入或阻塞感。

## 最终修复点

### 1) 蓝牙模式“净化运行”

进入 BLE 模式时主动清理语音链路，减少模式残留：

- 停止正在播放的 TTS
- 释放语音输入相关缓冲
- 解除 TTS 共享缓冲绑定

并在 BLE 模式下暂停以下循环工作：

- `cmdServer.tick()`
- UDP 状态广播

目标：让 BLE 键盘模式成为相对独立、低干扰的运行态。

### 2) 输入上报策略调整

从“高频 tap 风格上报”收敛为“键盘状态变化上报”，降低队列压力与发送抖动。

同时调整发送队列参数：

- 队列容量扩至 `24`
- 发送间隔约 `8ms`

### 3) 增加可观测性（串口指标）

增加每秒一次 `BLEDBG` 日志，关键字段：

- `q`：当前队列深度
- `enq`：累计入队
- `sent`：累计发送
- `drop`：累计丢弃
- `sat`：累计饱和
- `heap`：当前堆剩余
- `largest`：最大连续可用块

这样可以直接区分：

- 是发送拥塞（`q/sat/drop` 异常）
- 还是内存碎片/不足（`heap/largest` 异常）
- 或者只是外部链路波动

## 回归测试步骤

1. 进入 BLE 键盘模式，完成配对连接。
2. 连续输入短句、长串字符、快速重复按键。
3. 观察主机端是否有明显延迟、卡死、重复字符失控。
4. 串口同步观察 `BLEDBG`：
   - `drop` 持续增长且输入异常：优先看发送节流/队列参数。
   - `largest` 过低且波动大：优先看内存碎片与动态分配点。
5. 断开/重连后重复步骤 2-4，确认会话切换稳定。

## 现场应急建议

- 若现场复现且无法立刻改代码，先重启设备，确保 BLE 模式从干净状态进入。
- 禁止并行构建与刷机，避免 Windows 下 `.pio` 构建产物竞争导致的假故障。
- 优先抓串口指标再改代码，避免“猜测式修复”。

## 后续建议

- 将 `BLEDBG` 做成可开关（默认关闭，问题排查时开启）。
- 把 BLE 相关参数（队列长度、发送间隔）集中成配置常量，便于 A/B 调参。
- 新增自动化输入压测脚本（主机端）做回归，避免后续改动再次引入卡顿。
